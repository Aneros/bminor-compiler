# گزارش فنی فاز اول B-Minor

این گزارش معماری، الگوریتم‌ها، ساختار AST، مدیریت خطا و روش رنگ‌آمیزی نحوی پروژه را شرح می‌دهد.

## معماری

جریان پردازش:

```text
SourceFile ── Lexer ── جریان کامل توکن‌ها ────────────────┐
                   └─ خطاهای لغوی                      │
                                                      ▼
        حذف trivia و INVALID برای Parser ── AST ── Highlighter
                                           │          ├─ ANSI
                                           │          └─ HTML/CSS
                                           └─ خطاهای نحوی
```

`SourceFile` متن را تغییر نمی‌دهد و محل شروع خطوط را نگه می‌دارد. `Lexer` فقط مسئول واژه‌هاست. `Parser` نسخهٔ پالایش‌شدهٔ جریان توکن‌ها را می‌بیند؛ اطلاعات جریان اصلی از بین نمی‌رود. رنگ‌آمیز هم به توکن‌ها برای بازسازی دقیق متن و هم به AST برای شناخت نقش نام‌ها دسترسی دارد. رابط خط فرمان خروجی‌ها و خطاها را به فایل یا جریان‌های استاندارد هدایت می‌کند.

تمام منطق اصلی در C++17 و با کتابخانهٔ استاندارد نوشته شده است. Python صرفاً رانندهٔ آزمون‌های یکپارچه است. هیچ مولد Lexer/Parser یا پیاده‌سازی پروژهٔ دانشجوی دیگری استفاده نشده است.

خواندن فایل و stdin از `std::fread` همراه با بررسی `std::ferror` استفاده می‌کند؛ این API بخشی از کتابخانهٔ استاندارد C++ است و خطای خواندن را از پایان طبیعی فایل جدا می‌کند. فایل ورودی با `unique_ptr` و `fclose` مدیریت می‌شود. این تصمیم با آزمون رگرسیونِ ورودی استانداردِ متصل به پوشه بررسی شده است.

## طراحی تحلیلگر لغوی

روش انتخابی، ماشین حالت قطعیِ دستی است. انتخاب حالت اولیه با نویسهٔ جاری انجام می‌شود:

| نویسهٔ آغاز | حالت | شرط پایان |
| --- | --- | --- |
| حرف یا `_` | شناسه | نخستین نویسهٔ خارج از حرف/عدد/زیرخط |
| رقم | عدد صحیح | نخستین نویسهٔ غیررقم |
| فاصله، tab، CR، LF | فاصلهٔ سفید | نخستین نویسهٔ غیرفاصله |
| `"` یا `'` | رشته/کاراکتر با زیرحالت escape | کوتیشن متناظر یا خطا در انتهای خط/فایل |
| `//` | توضیح خطی | انتهای خط یا فایل |
| `/*` | توضیح بلوکی | نخستین `*/` یا خطا در EOF |
| عملگر یا جداکننده | تطبیق دو یا یک نویسه | طولانی‌ترین عملگر قابل تطبیق |
| سایر موارد | نامعتبر | یک کاراکتر UTF-8 یا یک بایت نامعتبر |

هر شناسه ابتدا کامل خوانده می‌شود و سپس عضویت در مجموعهٔ کلمات کلیدی بررسی می‌شود؛ بنابراین `returnValue` شناسه است و `return` کلمهٔ کلیدی. ابتدا `<=` بررسی می‌شود و سپس `<`، تا Maximal Munch رعایت شود. توضیح بر تقسیم اولویت دارد.

هر `Token` شامل نوع، لکسمِ دقیق، مقدار رمزگشایی‌شدهٔ اختیاری و محدودهٔ منبع است. نگهداشت جداگانهٔ لکسم و مقدار اجازه می‌دهد `"a\n"` در HTML دقیقاً همان متن نوشته‌شده باقی بماند، در حالی که مقدار آن شامل LF باشد. برای اعداد، رشتهٔ ارقام نگهداری می‌شود تا تبدیل به عددِ میزبان باعث سرریز نشود.

تعریف رسمی همهٔ دسته‌ها، محدودیت طول و escapeها در [lexer.md](lexer.md) آمده است. منظور از اعداد صحیح علامت‌دار، دامنهٔ مقدار است؛ `-` به‌صورت توکن مستقل وارد AST می‌شود تا `x-1` نیز درست تحلیل شود.

## طراحی Parser و گرامر

گرامر کامل در [bminor.ebnf](../grammar/bminor.ebnf) قرار دارد. Parser از روش بازگشتی نزولی با تصمیم دو‌توکنی برای پیشوند `IDENTIFIER :` استفاده می‌کند. این پیشوند اعلان را از دستور عبارت متمایز می‌کند. برای هر سطح تقدم عبارت، تابع مستقل وجود دارد؛ ترتیب فراخوانی توابع تقدم را پیاده می‌کند.

قاعدهٔ بازگشتی چپ مانند `E → E + T | T` به `E → T { + T }` تبدیل شده و با حلقه پیاده می‌شود. حلقه، AST را به چپ ترکیب می‌کند. انتساب و توان با بازگشت به راست ساخته می‌شوند. این انتخاب در آزمون‌های `a=b=c` و `2^3^4` بررسی شده است. جزئیات FIRST/FOLLOW و ابهام `else` در [grammar.md](grammar.md) توضیح داده شده‌اند؛ گرامر بدون توضیح به‌عنوان LL(1) معرفی نشده است.

`else` بلافاصله پس از دستور شاخهٔ then خوانده می‌شود و به نزدیک‌ترین `if` بدون else تعلق می‌گیرد. نوع‌ها و اعلان‌ها بازگشتی‌اند، اما هر مسیر بازگشت ابتدا توکن مصرف می‌کند. `for` سه عبارت اختیاری دارد؛ `print` یک یا چند عبارتِ جداشده با ویرگول می‌پذیرد و `return` می‌تواند بدون مقدار باشد.

## AST و مالکیت حافظه

`AstNode` یک ساختار برچسب‌دار است: `NodeKind` نوع گره را مشخص می‌کند و یال‌ها نام نقش دارند. نمونه‌ها:

| گره | نقش فرزندان |
| --- | --- |
| VarDecl | declared_type، initializer اختیاری |
| FuncDecl | declared_type، body اختیاری برای prototype |
| FunctionType | return_type، parameterها |
| ArrayType | length اختیاری، element_type |
| BinaryExpr / AssignExpr | left، right |
| IfStmt | condition، then، else اختیاری |
| CallExpr | callee، argumentها |
| ForStmt | initializer، condition، update اختیاری؛ body |

برای مثال، `x: integer = 1 + 2 * 3;` چنین ساختاری دارد:

```text
Program
  declaration: VarDecl "x"
    declared_type: TypeName "integer"
    initializer: BinaryExpr "+"
      left: IntegerLiteral "1"
      right: BinaryExpr "*"
        left: IntegerLiteral "2"
        right: IntegerLiteral "3"
```

مالکیت فرزندان با `std::unique_ptr` است؛ چرخهٔ مالکیت وجود ندارد و تخریب به‌صورت RAII انجام می‌شود. `type_annotation` در همهٔ گره‌ها ابتدا تهی است. نوع نوشته‌شده در اعلان در فرزند `declared_type` قرار دارد و با نتیجهٔ بررسی نوع در فاز بعد اشتباه گرفته نمی‌شود.

هر گره محدودهٔ نیمه‌باز منبع و اندیس توکن مرتبط را دارد. محدودهٔ BinaryExpr از شروع عملوند چپ است، ولی اندیس توکنش به عملگر اشاره می‌کند. محدودهٔ CallExpr از شروع callee است و اندیس مرتبط به پرانتز فراخوانی اشاره می‌کند. موقعیت توکنِ نام در گره IdentifierExpr و اعلان‌ها نگه داشته می‌شود و برای رنگ‌آمیزی دقیق استفاده می‌شود.

## مدیریت خطا

Lexer برای نویسهٔ ناشناخته INVALID می‌سازد و ادامه می‌دهد. رشتهٔ ناتمام در انتهای خط متوقف می‌شود تا خط بعد قابل تحلیل باشد. توضیح بلوکی ناتمام تا EOF خوانده می‌شود. هر خطا کد پایدار و محدودهٔ منبع دارد.

Parser پس از گزارش خطا تا `;`، `}` یا شروع یک اعلان/دستور قابل تشخیص جلو می‌رود. سمیکالن مصرف می‌شود؛ آکولاد بسته برای بلوک نگه داشته می‌شود. در سطح فایل، آکولاد اضافی مصرف می‌شود تا حلقهٔ بازیابی پیشرفت کند. ساختار خراب با ErrorStmt نشان داده می‌شود و دستورهای درست بعدی در AST می‌مانند. بازگشت‌های عمیق و رشد عمق AST با حد ایمنی ۲۵۶ کنترل می‌شوند.

خطاها در stderr، مرتب‌شده بر اساس موقعیت، نمایش داده می‌شوند. قالب متنی شامل فایل، خط، ستون و caret است؛ JSON شامل phase، code، message و span است. وجود خطای منبع کد خروج ۱ می‌دهد، ولی AST جزئی و خروجی رنگی همچنان ساخته می‌شوند.

## رنگ‌آمیزی وابسته به AST

ابتدا دستهٔ پایهٔ توکن تعیین می‌شود. سپس AST پیمایش می‌شود:

- نام FuncDecl، چه prototype و چه تعریف، دستهٔ تابع می‌گیرد.
- نام پارامتر با FunctionType نیز دستهٔ تابع می‌گیرد.
- در CallExpr، اگر callee یک IdentifierExpr یا شناسهٔ داخل پرانتز باشد، همان توکن نام تابع می‌گیرد.
- باقی شناسه‌ها دستهٔ متغیر دارند؛ توکن‌های دارای خطای تشخیصی قرمز و زیرخط‌دار می‌شوند.

این روش از جست‌وجوی نام یا عبارت منظم برای حدس‌زدن تابع استفاده نمی‌کند. در نتیجه متن `f()` داخل توضیح یا رشته، فراخوانی محسوب نمی‌شود و یکسان‌بودن املای نام تابع و متغیر باعث یکسان‌شدن رنگ همهٔ رخدادها نمی‌شود. تشخیص ارجاع بدون فراخوانی یا نوع callee مرکب، به جدول نمادها در فاز بعد نیاز دارد.

ANSI فقط کدهای رنگ را پیرامون لکسم‌ها قرار می‌دهد. HTML متن و نام فایل را escape می‌کند، CSS را داخل فایل قرار می‌دهد و از `<pre><code>` استفاده می‌کند. فاصله‌ها و توضیحات از جریان توکن اصلی بازسازی می‌شوند؛ AST برای تولید مجدد متن استفاده نمی‌شود، چون جزئیات قالب‌بندی در AST وجود ندارند.

## پیچیدگی و توسعهٔ بعدی

اسکن روی متن یک گذر دارد؛ تبدیل offset به موقعیت با جست‌وجوی دودویی در شروع خطوط انجام می‌شود. در مجموع هزینهٔ موقعیت‌یابی `O(T log L)` است که T تعداد توکن‌ها و L تعداد خطوط است. Parser روی توکن‌ها حرکت رو به جلو دارد و با محدودیت عمق، هزینهٔ خطی نسبت به ورودی دارد. پیمایش AST و تولید خروجی نسبت به تعداد گره‌ها/توکن‌ها و طول خروجی خطی است؛ علامت‌گذاری خطاها از جست‌وجوی دودویی استفاده می‌کند.

در فاز بعد می‌توان جدول نمادها، حوزه‌ها و حل نام را به پیمایش AST افزود، فیلد type_annotation را پر کرد و سپس بررسی نوع، گراف فراخوانی و CFG را پیاده کرد. هیچ‌یک از آن بخش‌ها در خروجی این فاز به‌عنوان انجام‌شده معرفی نشده است.
